# 05 · OS 自动化与权限

> 这是 WorkBuddy 的**支柱②**：让 agent **真正能动手操控电脑**——截图感知、鼠标点击、键盘输入、剪贴板、跨 App 编排。
>
> 本篇覆盖：能力清单、技术实现（macOS/Windows 双平台）、**权限与安全模型**（这是信任的地基）、可靠性策略。
> 参考：[Claude Computer Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)、腾讯 WorkBuddy 的 OS 操控、Recall 的隐私教训。

---

## 一、能力清单

按"感知 → 操作 → 编排"分层：

| 类别 | 工具 | MVP/P1 | 说明 |
|------|------|:---:|------|
| **感知** | `screenshot` | P1 | 截全屏 / 指定窗口 / 区域 |
| | `get_active_window` | P1 | 当前 App + 窗口标题 |
| | `get_selection` | P1 | 用户选中的文本（多来源） |
| | `get_clipboard` / `set_clipboard` | P1 | 读/写剪贴板 |
| | `list_windows` | P1 | 所有窗口（供 agent 定位目标） |
| **操作** | `click` | P1 | 点击坐标 / UI 元素 |
| | `double_click` / `right_click` | P1 | |
| | `type_text` | P1 | 输入文本（含中文） |
| | `press_key` / `hotkey` | P1 | 按键 / 组合键 |
| | `scroll` / `move_mouse` | P1 | |
| | `launch_app` / `quit_app` | P1 | 启动/退出 App |
| | `open_url` / `open_file` | MVP | 系统默认打开（低风险，先有） |
| **编排** | 复合：感知→操作循环 | P1 | Computer Use 循环（见 §三） |

> **MVP 只放低风险的 `open_url`/`open_file`**；真正的"动手"操作（截图/点击/键盘）整体放 P1，因为权限/可靠性需先打磨。

## 二、速唤浮窗（Quick Buddy）—— OS 集成的"门面"

速唤浮窗是用户感知"OS 集成"的首要触点，也是低风险高价值的入口。

### 2.1 形态

- **全局热键** `⌥Space`（macOS）/ `Alt+Space`（Windows）唤起，屏幕中央弹出小浮窗（不是主窗口）。
- 浮窗自动捕获**当前上下文**：
  - 当前 App 名 + 窗口标题
  - 用户选中的文本（若 API 可获取，否则引导用户复制）
  - 剪贴板内容（可选，需权限）
  - （P1）当前屏幕截图缩略图
- 用户输入问题 → 带上下文调用 agent → 答案浮层显示。
- `Esc` 关闭；结果可"送入主工作台继续"。

### 2.2 选区获取（多来源降级）

| 平台 | 首选 | 降级 |
|------|------|------|
| macOS | Accessibility API (`AXSelectedText`) | 模拟 `⌘C` 读剪贴板（侵入性略高） |
| Windows | UIAutomation (`TextPattern.GetSelection`) | 模拟 `Ctrl+C` 读剪贴板 |

> 设计：**默认走非侵入的 API**；模拟按键复制只在 API 失败时用，且明确告知用户"已复制选区"。

### 2.3 实现技术

- **全局热键**：`global-hotkey`（Tauri 官方插件）。
- **浮窗**：独立 Tauri 窗口，`transparent + always_on_top + decorations:false + resizable:false`，定位到屏幕中央/鼠标附近。
- **唤起动画**：CSS，<150ms。

## 三、Computer Use：感知-操作循环

agent 操控 GUI 的标准模式（Claude Computer Use 范式）：

```
┌──────────────────────────────────────────────────────────┐
│  1. screenshot()  ──→ 图片                              │
│  2. 视觉模型(多模态) 分析: "看到'保存'按钮在 (320, 480)"  │
│  3. click(320, 480)  ──→ Rust 执行鼠标点击              │
│  4. screenshot()  ──→ 确认点击效果                       │
│  5. (循环直至任务完成 或 触发中止条件)                    │
└──────────────────────────────────────────────────────────┘
```

**我们的差异**：优先用**语义 UI 元素**（Accessibility/UIAutomation 树）而非纯像素坐标——更可靠、抗分辨率/主题变化。坐标点击作为兜底。

### 3.1 平台技术栈（Deno 进程）

> 技术栈已切到 **deno desktop**（spike 验证，见 [07](./07-deno-desktop-spike验证.md)）。下表标注每项能力的 spike 验证状态。

| 能力 | 实现 | spike 验证 | 备注 |
|------|------|:---:|------|
| **终端/shell** | `@lydell/node-pty`（mac/linux），`child_process.spawn`（win） | ✅ | pty.spawn 可起；吸取 WorkBuddy Windows 教训 |
| **托盘** | `Deno.Tray` | ✅ | 文档未写但 API 存在 |
| **窗口** | `Deno.BrowserWindow` | ✅ | 多窗口 |
| **App/文件打开** | `Deno.open` / `Deno.Command` | ✅ | Deno 原生 |
| **剪贴板** | Web Clipboard API / Deno 原生 | 待验 | webview 侧用 Web 标准 |
| **文件监听** | `chokidar` | 推断 | npm 兼容 |
| **鼠标/键盘** | nut-js 或 AppleScript/PowerShell | 待验 | Computer Use P1 |
| **截图** | Deno screen capture / 系统命令 | 待验 | P1 |
| **UI 元素树** | Accessibility API（FFI 或 osascript） | 待验 | P1 |
| **全局热键** | ❌ **deno desktop 暂无** | ❌ | **缺口**：速唤浮窗 P1 用 `Deno.dlopen`（FFI）调系统 API 或 native 插件解决 |

**统一抽象**：Deno 进程定义 `OsBridge` 接口（TS），每平台实现，供 agent 工具调用。

```typescript
// domains/os/node/bridge.ts
interface OsBridge {
  screenshot(target?: "screen" | "window" | Rect): Promise<Buffer>;
  getActiveWindow(): Promise<WindowInfo>;
  getSelection(): Promise<string>;           // 选中文本（Accessibility/降级复制）
  click(target: Coord | { elementQuery: string }): Promise<void>;
  typeText(text: string): Promise<void>;
  pressKey(key: string): Promise<void>;
  clipboardGet(): Promise<ClipboardContent>;
  clipboardSet(c: ClipboardContent): Promise<void>;
  launchApp(id: string): Promise<void>;
  runShell(cmd: string): Promise<ShellResult>;  // 经 node-pty
}
```

> WorkBuddy 已验证：它用 `@lydell/node-pty` 做 shell/自动化。我们同款。Computer Use 的视觉理解走多模态 LLM（pi 支持图片输入）。

## 四、权限与安全模型（信任地基）

> **Recall 翻车的核心教训**：能力强但权限/透明度不足 → 用户不信任。WorkBuddy 必须把"权限"做成一等公民。

### 4.1 三层权限模型

```
┌──────────────────────────────────────────────────┐
│  L1: 操作系统权限 (TCC / 系统授权)                 │
│      macOS: 屏幕录制/辅助功能/输入监控            │
│      Windows: UIAutomation 默认可用; 截图需设置    │
├──────────────────────────────────────────────────┤
│  L2: WorkBuddy 能力开关 (用户在设置里总控)         │
│      截图 / 鼠标 / 键盘 / 剪贴板 / 文件写入       │
│      默认全关, 用到即时弹窗申请                   │
├──────────────────────────────────────────────────┤
│  L3: 任务级确认 (高风险操作即时确认)               │
│      发送邮件 / 删除文件 / 付款 / 不可逆操作      │
│      agent 必须暂停, 弹窗显示"将要做X", 用户确认   │
└──────────────────────────────────────────────────┘
```

### 4.2 L1 系统授权（一次性引导）

首次启用某能力时，引导用户到系统设置授权：
- **macOS**：
  - 截图 → 系统设置 → 隐私 → 屏幕录制
  - 点击/键盘 → 系统设置 → 隐私 → 辅助功能
  - 剪贴板监听 → 输入监控
- **Windows**：UIAutomation 多数情况免授权；截图可能需"让应用控制你的设备"。

提供"检测授权状态"API（macOS 用 `tccutil`/`Accessibilidade` 查询），未授权时清晰指引用户去授权页。

### 4.3 L2 能力开关

```
设置 → OS 自动化权限
  ☐ 截屏与屏幕识别
  ☐ 鼠标控制（点击/拖拽）
  ☐ 键盘输入
  ☐ 读取剪贴板
  ☐ 写入剪贴板
  ☐ 启动/退出应用
  ☐ 文件写入范围：[ 选择目录... ]   （默认 ~/Documents, ~/Desktop）
```

每项默认 **关闭**。agent 工具执行前，主进程 `permissions.ts` + pi 的 `beforeToolCall` 钩子仲裁：
- 工具声明 `requires: ["screenshot","mouse"]`
- 仲裁器检查这俩开关是否开 → 未开则**拒绝并返回结构化错误**，UI 提示"需开启 XX 权限"。

### 4.4 L3 任务级确认（高风险操作）

定义"敏感动作"清单，触发时**强制暂停 + 弹窗**：

| 类别 | 触发条件 | 确认方式 |
|------|----------|----------|
| 不可逆删除 | `delete_file` / 清空回收站 / 卸载 | 文字确认（输入文件名） |
| 对外发送 | 发邮件 / 发消息 / 上传 | 简短确认 |
| 付款/金融 | 检测付款页面/金融 App 操作 | 强确认 |
| 大批量 | 连续操作 > N 次自动汇总确认 | 汇总确认 |

实现：agent loop 在调用敏感工具前，**不直接 invoke**，而是 `emit('confirm_required', {tool, args})` 给前端，前端弹窗，用户决定后继续/取消。这是"做减法"的安全版——**宁可多问，不可乱动**。

### 4.5 数据流透明面板

每次 agent 任务可在 UI 展开"做了什么"时间线：
```
12:01:03  read_clipboard       → 读取剪贴板(3行文本)
12:01:04  model:glm-4          → 调用(进 120 token)
12:01:05  screenshot           → 截屏(当前: 飞书表格)
12:01:06  model:glm-4(视觉)    → 分析截图
12:01:07  click(320,480)       → 点击 [已确认]
12:01:08  type_text "已完成"   → 输入
```
**敏感行高亮**（如截屏/发送）。这直接对冲"AI 偷偷干活"的不信任，是信任的地基。

## 五、可靠性策略（支柱①在 OS 层的落地）

OS 自动化是 agent 最易失败、最伤信任的环节。策略：

1. **语义优先，像素兜底**：能通过 Accessibility/UIAutomation 定位元素就不点坐标——抗分辨率/主题/语言变化。
2. **每步可验证**：操作后 `screenshot` 自检，发现不符则停止并报错，而非盲下一步。
3. **超时与步数上限**：单任务 Computer Use 循环上限（如 20 步），超出强制暂停等用户。
4. **明确失败语义**：工具失败返回结构化 error（`ELEMENT_NOT_FOUND`/`APP_NOT_RUNNING`/`PERMISSION_DENIED`），agent 据此决定重试/换法/问用户。
5. **可随时中断**：热键 `Esc`（长按）或托盘"停止"按钮，立即终止 OS 操作循环。
6. **沙箱演练**（P2）：高风险任务先在"预览模式"展示将执行的步骤，用户批准后再实操。

## 六、macOS 与 Windows 差异速查

| 维度 | macOS | Windows |
|------|-------|---------|
| 截图授权 | 屏幕录制 TCC | 设置 > 隐私 > 截图边界 |
| 控制授权 | 辅助功能 TCC | UIAutomation 默认免授权 |
| 中文输入 | `typeText`（nut-js / AppleScript） | 直接 |
| UI 树标准 | Accessibility (AX) | UIAutomation |
| 脚本桥梁 | AppleScript（备选） | PowerShell（备选） |
| 窗口管理 | 简单（Space 限制） | 更灵活（多桌面/位置） |

> **MVP 平台优先级**：macOS 先（用户群偏 Mac），Windows 紧随。Linux 后置。

## 七、不做的事（安全边界）

- ❌ **不静默监听全局键盘/鼠标**（不做 keylogger 式的全局监控；Recall 的反例）。
- ❌ **不在后台持续录屏**；截图只在任务执行期间，按需单次。
- ❌ **不绕过系统 TCC**；尊重系统授权。
- ❌ **不自动处理支付/密码**；检测到敏感场景强制人工确认。
- ❌ **不向云端发送截图原始数据**（除非用户显式选择云端视觉模型且知情）。

## 八、与支柱①②③的协同

OS 自动化（②）与文档引擎（③）天然协同：典型场景是"从 App A 抽数据 → 处理 → 写成 docx"。

```
速唤浮窗感知"当前在看飞书表格"
  → screenshot + 视觉模型提取表格数据 (OS②)
  → write_xlsx 生成结构化 xlsx (文档③)
  → 立即迭代: "加个环比图" → edit_xlsx (文档③)
全程 agent 工具白名单收敛、权限逐项确认 (安全)
```

这种"感知→处理→产出"的闭环，是 WorkBuddy 区别于"只聊天"和"只读文档"产品的核心。
