# 04 · 文档处理引擎

> 这是 WorkBuddy 的**支柱③**，也是相对腾讯 WorkBuddy（飞书生态文档）最重要的自主能力：
> **不依赖 MS Office / WPS 安装、不依赖云，在本地完成 docx / xlsx / pptx / pdf / csv / md 的读、写、编辑。**
>
> 本篇给出每个格式的**最佳库选型**、**编辑难题的破解方案**、**AI agent 调用接口**和**分层架构**。

---

## 一、核心难题：编辑（EDIT）远比创建（CREATE）难

绝大多数 Office 库**只能创建**，不能编辑已有文件。而 AI agent 的核心场景恰恰是**迭代编辑**（"把标题改了""加一页"）。

| 路径 | 优点 | 缺点 | 何时用 |
|------|------|------|--------|
| **(a) 纯 JS/Rust 库** | 进程内、零依赖、快 | 编辑能力弱（多为创建专用） | 读/创建优先 |
| **(b) LibreOffice headless 转换** | 通用、保真 | 只擅长格式转换，不擅长结构化编辑 | 转 PDF / 渲染 / 兜底 |
| **(c) Python sidecar**（python-docx/-pptx/openpyxl） | **编辑能力最强** | 要打包 Python | docx/pptx 自由编辑 |
| **(d) docxtemplater 模板填充** | 纯 JS、快 | 仅"填空"，非自由编辑 | 模板驱动的文档生成 |
| **(e) Office.js / COM / WPS 自动化** | 保真最高 | **破坏跨平台**、依赖已装 Office | ❌ 不用 |

**WorkBuddy 采用 (a)+(b)+(c)+(d) 混合分层**：默认走主进程 JS 库（最快、零 sidecar），编辑短板由 Python sidecar 补，格式转换交给 LibreOffice。

> **对照 WorkBuddy（腾讯）**：其文档引擎是闭源 `@tencent/docs-engine`（C++ `start_server_addon.node`，不可复用）。我们用**开源 JS 栈 + Python sidecar** 对等实现，见 [00](./00-WorkBuddy逆向调研.md)。

## 二、分层架构

```
┌─────────────────────────────────────────────────────────────────┐
│            Agent (pi AgentTool 调用, 主进程内)                    │
│   read_doc / write_docx / write_xlsx / write_pptx /              │
│   edit_docx / edit_xlsx / edit_pptx / doc_to_pdf                 │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 主进程内函数调用
┌───────────────────────────▼─────────────────────────────────────┐
│        主进程 doc-engine 模块 (Node, 路由层)                      │
│   按 {格式 × 操作 × 是否需高保真} 路由到下面三层之一              │
├─────────────────┬─────────────────────┬─────────────────────────┤
│  Layer 1: 进程内 │  Layer 2: Python     │  Layer 3: LibreOffice   │
│  JS 库 (主进程)   │  sidecar (懒启动)     │  headless (懒启动)       │
│  (默认, 最快)    │  (编辑专用)           │  (转换/渲染/兜底)        │
│                  │                       │                         │
│  docx (dolanmiu) │  python-docx          │  soffice --convert-to   │
│  exceljs/xlsx    │  python-pptx          │  soffice 渲染幻灯片      │
│  pptxgenjs       │  openpyxl             │                         │
│  mammoth         │                       │                         │
│  docxtemplater   │                       │                         │
│  pdf-parse       │                       │                         │
│  marked          │                       │                         │
└─────────────────┴─────────────────────┴─────────────────────────┘
```

**路由原则**：
- **READ** → Layer 1（JS，主进程内，最快）。
- **CREATE（生成新文件）** → Layer 1（JS）。
- **EDIT（编辑现有文件）**：
  - xlsx → Layer 1 `exceljs`（读改写，主进程内）。
  - docx → **模板填充** Layer 1 `docxtemplater`（JS）；**自由编辑** Layer 2 Python。
  - pptx → **必须 Layer 2 Python**（无 JS 编辑方案）。
- **格式转换（→PDF）/ 渲染幻灯片为图片** → Layer 3 LibreOffice。

## 四、AI agent 工具接口设计

每个工具是一个 pi `AgentTool` → 在主进程内调 JS 库或 sidecar。下面给 schema 与返回。

### 4.1 `read_doc`（通用读取，喂 LLM）

```typescript
// 读任意文档，返回适合 LLM 消费的文本/结构化内容
{
  name: "read_doc",
  schema: {
    path: string,                  // 绝对路径或相对项目目录
    max_chars?: number,            // 截断保护(默认 50000)
    as?: "text" | "structured" | "tables"  // 文本 / 带结构 / 仅表格
  },
  // 返回
  result: {
    kind: "docx"|"xlsx"|"pptx"|"pdf"|"csv"|"md",
    text: string,                  // 主体文本
    tables?: Table[],              // xlsx/docx 的表格(结构化)
    slides?: Slide[],              // pptx 的幻灯片文本
    images?: { page:number, path:string }[],  // 无法抽文本时渲染成图(供视觉模型)
    truncated: boolean
  }
}
```
- **路由**：docx/xlsx/csv/md/pdf → 主进程 JS 库；pptx → Python sidecar（python-pptx 抽文本）。
- **降级**：若 pptx/pdf 抽文本质量差，LibreOffice 渲染成图片，返回 `images` 让 agent 用多模态模型理解。

### 4.2 `write_docx` / `write_xlsx` / `write_pptx`（创建）

```typescript
{
  name: "write_docx",
  schema: {
    path: string,
    title?: string,
    sections: Section[],           // 结构化内容
    style?: "report" | "letter" | "minimal"
  }
  // Section = { heading?:string, paragraphs?:string[], table?:TableData, image?:{path,caption} }
  // → 主进程 docx (dolanmiu) 生成
}

{
  name: "write_xlsx",
  schema: {
    path: string,
    sheets: { name:string, data:Cell[][], headers?:string[], chart?:ChartSpec }[]
  }
  // → 主进程 exceljs 生成
}

{
  name: "write_pptx",
  schema: {
    path: string,
    slides: { layout:string, title?:string, body?:string, bullets?:string[], image?:string }[]
  }
  // → 主进程 pptxgenjs 生成(JS, 无需 sidecar)
}
```

**设计要点**：agent 输出**结构化 JSON**，由主进程 JS 库渲染成文档——而非让模型直接吐 OOXML。这是可靠性的关键（模型不擅长精确 XML）。

### 4.3 `edit_docx` / `edit_xlsx` / `edit_pptx`（编辑现有文件）

```typescript
// docx 模板填充(纯 JS docxtemplater, MVP 首选编辑路径)
{
  name: "edit_docx",
  schema: {
    path: string,
    mode: "template" | "freeform",
    // template 模式: 文档含 {{name}} 占位符, 这里给值
    vars?: Record<string, string|number>,
    // freeform 模式: 结构化指令, 转交 python-docx
    changes?: DocChange[]
  }
  // DocChange =
  //   { op:"replace_text", find:string, with:string }
  // | { op:"insert_paragraph", after:string, text:string }
  // | { op:"append_section", heading:string, body:string }
  // | { op:"update_table_cell", table:int, row:int, col:int, value:string }
}

{
  name: "edit_xlsx",
  schema: { path:string, changes: XlsxChange[] }
  // XlsxChange =
  //   { op:"set_cell", sheet:string, cell:"A1", value:any, formula?:string }
  // | { op:"add_row", sheet:string, row:any[] }
  // | { op:"add_sheet", name:string }
  // → 主进程 exceljs (读改写)
}

{
  name: "edit_pptx",
  schema: { path:string, changes: PptxChange[] }
  // PptxChange =
  //   { op:"replace_text", slide:int, find:string, with:string }
  // | { op:"add_slide", layout:string, title?:string, body?:string }
  // | { op:"add_image", slide:int, path:string }
  // → Python sidecar python-pptx (P1)
}
```

### 4.4 `doc_to_pdf`（格式转换）

```typescript
{
  name: "doc_to_pdf",
  schema: { src:string, out?:string }
  // → LibreOffice: soffice --headless --convert-to pdf --outdir <dir> <src>
}
```

## 五、Python sidecar 设计

### 5.1 为何需要 / 何时启动

- **必须 sidecar** 的场景：pptx 任意读写编辑、docx 自由编辑、复杂保真 xlsx 编辑。
- **懒启动**：sidecar 不常驻，首次用到才拉起；用一个轻量"预热"在用户首次配置时可选。
- **打包**：`PyInstaller --onefile` 打成单二进制，随 Tauri `externalBin` 分发，每平台一个（`docpy-x86_64-apple-darwin` 等）。

### 5.2 通信协议（stdin/stdout JSON-RPC）

```jsonc
// → sidecar
{"id":"1","method":"edit_docx","params":{"path":"...","changes":[...]}}

// ← sidecar
{"id":"1","result":{"ok":true,"path":"...","pages":3}}
// 或
{"id":"1","error":{"code":"PARSE_FAIL","message":"..."}}
```

主进程用 Node `child_process.spawn` 管理 sidecar 生命周期，加超时与崩溃重启。

### 5.3 sidecar 暴露的方法

| method | 库 | 说明 |
|--------|----|----|
| `read_pptx` | python-pptx | 抽文本/表格 |
| `edit_docx_freeform` | python-docx | 自由编辑 |
| `edit_pptx` | python-pptx | 幻灯片编辑/增删 |
| `edit_xlsx_highfid` | openpyxl | 高保真 xlsx 编辑（exceljs 不够时） |
| `render_to_images` | python-pptx + LibreOffice | 幻灯片转图（视觉输入） |

## 六、LibreOffice headless 用法与陷阱

### 6.1 用途
- **格式转换**：docx/xlsx/pptx → pdf；docx → html；xlsx → csv。
- **渲染为图片**：pptx → pdf → pdftoppm → png（给视觉模型）。
- **损坏文件恢复**：打不开的旧格式用它转一道。

### 6.2 调用

```bash
soffice --headless --norestore \
  -env:UserInstallation=file:///tmp/lo-profile-wb-$$ \
  --convert-to pdf --outdir /tmp/out input.docx
```

### 6.3 ⚠️ 陷阱与对策
| 陷阱 | 对策 |
|------|------|
| **profile 锁竞争**（并发调用共享 profile 报锁） | **每次调用给唯一 `UserInstallation` 路径**（上例 `-env:UserInstallation=...`） |
| **首次冷启动慢**（2-5s） | sidecar 化：常驻一个 soffice listener，用 socket 通信（UNO API）；或预暖 |
| **体积大**（~700MB） | 作为"可选下载组件"，用到 PDF/转换时提示用户安装；或打包精简版 |
| **随包分发授权** | MPL-2.0 允许随包分发，但需附版权声明 |

> **MVP 决策**：PDF 转换列为 P1。MVP 先支持读 PDF（pdf-extract）+ 生成 docx/xlsx/pptx；"导出 PDF"放到 P1，届时再处理 LibreOffice 分发。

## 七、MVP vs P1 能力边界

| 能力 | MVP | P1 | 备注 |
|------|:---:|:---:|------|
| 读 docx/xlsx/csv/md | ✅ | | 主进程 JS（mammoth/exceljs） |
| 读 pdf（文本） | ✅ | | pdf-parse |
| 读 pptx | ✅ | | Python sidecar |
| 创建 docx | ✅ | | docx（dolanmiu, JS） |
| 创建 xlsx（含图表） | ✅ | | exceljs（JS） |
| 创建 pptx | ✅ | | pptxgenjs（JS） |
| **编辑 xlsx** | ✅ | | exceljs（JS，读改写） |
| **编辑 docx（模板填充）** | ✅ | | docxtemplater（JS） |
| 编辑 docx（自由） | | ✅ | python-docx sidecar |
| **编辑 pptx** | | ✅ | python-pptx sidecar |
| 导出 PDF | | ✅ | LibreOffice |
| 幻灯片渲染为图（视觉） | | ✅ | LibreOffice |

**MVP 落地关键路径**（无需 Python/LibreOffice 即可跑通）：
> 读 xlsx → 分析 → 生成新 xlsx（或编辑现有 xlsx）→ 读/写/模板编辑 docx。
> 这条路径全在主进程 JS 完成，零 sidecar，体验最轻。

## 八、可靠性原则（呼应"pi 极简可靠"）

1. **结构化驱动，不吐 XML**：agent 输出 JSON 结构，库负责渲染——避免模型生成格式错误的 OOXML。
2. **失败可见**：任何文档操作失败，向 agent 返回结构化 error（`PARSE_FAIL`/`WRITE_DENIED`/`UNSUPPORTED`），agent 据此决定重试或换路径。
3. **能力探测**：agent 调工具前，工具 schema 已声明支持的范围；超范围直接拒绝，而非半成品输出。
4. **沙箱写路径**：所有写操作只能落在 `artifacts/` 或用户授权目录（见 [05](./05-OS自动化与权限.md)）。
5. **版本不丢**：编辑前自动存 `artifact_versions`，失败可回退。
