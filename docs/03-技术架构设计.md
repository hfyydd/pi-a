# 03 · 技术架构设计

> 本篇是 WorkBuddy（我们）的**技术架构蓝图**，是后续编码的直接依据。
> 基于三件已验证事实：① pi v0.80.3 真实 API（本地 `~/Desktop/pi-mono`）；② WorkBuddy（腾讯）实现级拆解（见 [02-WorkBuddy完整拆解](./02-WorkBuddy完整拆解.md)）；③ **deno desktop spike 全部通过**（7 项测试，见 [07-deno-desktop-spike验证](./07-deno-desktop-spike验证.md)）。
> **设计哲学：相对 WorkBuddy 的"双层 sidecar + ACP 协议 + 反向委托"做系统性减法，用 deno desktop 的 in-process bindings 让 pi 与 UI 同进程零 IPC，钩子直调——用 pi 的极简哲学贯穿架构。**

---

## 一、设计哲学与架构总览

### 1.1 与 WorkBuddy 的对照：减法设计

WorkBuddy（腾讯）的架构是**生产级、重型**的：Electron UI 壳 ← ACP/HTTP/SSE → cbc sidecar（@openai/agents）+ 反向委托（`_codebuddy.ai/delegateTool`）+ OS 级沙箱 + 多 sidecar。它解决了腾讯规模下的稳定性/复用性，但对我们 MVP 是过度工程。

我们的策略：**用 deno desktop 的 in-process bindings，让 pi 与 UI 在同进程（进程组）内，零跨进程 IPC**。deno desktop 的"后端与 webview 走 in-process channels，非 socket"天生契合我们"钩子直调"哲学。

| 维度 | WorkBuddy（腾讯） | **WorkBuddy（我们）** | 减法理由 |
|------|-----------|-----------|----------|
| **桌面框架** | Electron + cbc sidecar | **deno desktop 2.9** | in-process bindings（零 IPC）+ ~40MB 包体 + 单机交叉编译 + 内置更新 |
| **Agent 进程** | cbc 独立 sidecar + ACP 协议 | **Deno runtime 直跑 pi** | 零协议开销；pi Agent 类天然支持后续拆分 |
| **UI ↔ 后端通信** | ipcMain/ipcRenderer 跨进程 | **`win.bind` in-process bindings** | 同进程通道，无 socket 往返（spike 验证） |
| **工具执行** | 反向委托（`_codebuddy.ai/delegateTool`） | **钩子直调**（execute 内直调主进程能力） | 同进程函数调用 |
| **MCP** | 三 transport + MCP=subagent | **MVP 不做** | 先验证核心价值，P1 再上生态扩展 |
| **文档引擎** | 闭源 SaaS docs-engine | **JS 开源栈 + 懒启动 sidecar** | 不绑生态，MVP 零 sidecar |
| **存储** | better-sqlite3（Node 原生） | **node:sqlite**（Deno 内置） | spike 验证 better-sqlite3 在 Deno 不兼容，node:sqlite 完美替代 |
| **OS 沙箱** | Network Extension + sandbox-cli | **MVP 不做，P1 文件快照** | OS 扩展门槛过高，MVP 用权限+快照够用 |

**核心特征**：
1. **pi 在 Deno runtime**（spike 验证 `new Agent()` + 真实 LLM 流式全通）——所有 provider SDK / 原生 fetch 网络 / 文件零摩擦，**无 CORS**。
2. **in-process bindings**（spike 验证 `win.bind` OK）——Deno 侧与 webview 走进程内通道，**非 socket IPC**，工具调用/事件推送零往返。
3. **能力模块和 pi 同 runtime**——工具 execute 直调，零跨进程（区别于 WorkBuddy 的反向委托）。
4. **sidecar 懒启动**——MVP 多数路径在 Deno runtime 内 JS 完成。
5. **架构边界固定**——能力下沉到 domain，Agent 类天然支持跨进程，保证 MVP→P1→P2 平滑演进。

### 1.3 deno desktop 进程模型（与 Electron 的本质区别）

```
Electron: 主进程(Node) ←ipcMain/ipcRenderer→ 渲染进程(Chromium)  [跨进程序列化]
deno desktop: 单 Deno runtime + webview 线程/进程组               [in-process channels]
```

deno desktop 的官方原话（[bindings 文档](https://docs.deno.com/runtime/desktop/bindings/)）：
> "Bindings are not IPC. The Deno runtime and the rendering backend run as threads/processes inside the same address space (CEF) or coordinated process group (WebView). Calls go through in-process channels... avoids the cross-process round-trip that socket-based IPC frameworks (Electron's ipcMain/ipcRenderer, Tauri's invoke) impose."

**这正好是我们追求的"主进程直跑 pi + 钩子直调"——deno desktop 天生如此，无需费力。** spike 已验证 `win.bind("ping", handler)` 注册、webview 侧 `bindings.ping()` 调用全通。

### 2.2 AgentProvider 抽象（吸收 WorkBuddy 双模式发现）

WorkBuddy 逆向揭示它有 **CloudAgentProvider（HTTP 直连云端）** 和 **LocalAgentProvider（经 ACP 连本地 cbc sidecar）** 双模式（见 [02-WorkBuddy完整拆解](./02-WorkBuddy完整拆解.md) §8.1）。

我们 MVP 是"Deno runtime 直跑 pi"，但**抽象出 `AgentProvider` 接口**，让 pi 成为 `LocalProvider` 的一种实现，未来可平滑加 `CloudProvider`。

export class LocalPiProvider implements AgentProvider {
  readonly id = "local" as const;

### 2.3 真实嵌入实现（基于 spike 验证的 API）

```typescript
// agent/engine.ts
import { Agent } from "npm:@earendil-works/pi-agent-core@0.80.3";
import { createModels } from "npm:@earendil-works/pi-ai@0.80.3";
import { deepseekProvider } from "npm:@earendil-works/pi-ai@0.80.3/providers/deepseek";
import { getApiKey } from "../infra/keychain.ts";       // keytar
import { checkToolPermission, logToolCall } from "./permissions.ts";
import { docTools, osTools, memoryTools } from "./tools/index.ts";

// 全局 Models 集合（spike 验证可用）
const models = createModels();
models.setProvider(deepseekProvider());  // 按用户设置动态注册

export function createWorkBuddyAgent(win: BrowserWindow, cfg: {
  modelProvider: string; modelId: string; systemPrompt: string;
  tools?: AgentTool<any>[];
}) {
  const model = models.getModel(cfg.modelProvider, cfg.modelId)!;
  const agent = new Agent({
    initialState: {
      model,
      systemPrompt: cfg.systemPrompt,
      tools: cfg.tools ?? [...docTools, ...osTools, ...memoryTools],
    },
    // LLM 流式：经 Models（Deno 原生 fetch，无 CORS）
    streamFn: (m, ctx, opts) => models.streamSimple(m, ctx, opts),
    getApiKey: async (provider) => (await getApiKey(provider)) ?? undefined,
    beforeToolCall: async (ctx) => {
      const d = await checkToolPermission(ctx.toolCall.name, ctx.args);
      return d.allow ? undefined : { block: true, reason: d.reason };
    },
    afterToolCall: async (ctx) => { await logToolCall(ctx.toolCall.name, ctx.args, ctx.isError); },
    toolExecution: "parallel",
  });

  // 订阅事件流 → 经 win（in-process）推送 UI
  agent.subscribe(async (event) => {
    win.bind("onAgentEvent", event);  // 见 §五 in-process bindings
  });

  return agent;
}
```

> **pi API 与宿主无关**：spike 证明同样的 `new Agent({...})` 代码在 Deno 与 Node 行为一致。切换桌面框架不波及 pi 接入代码。

### 3.2 权限模型（beforeToolCall 钩子，对应 WorkBuddy DeferExecute 但更简洁）

```typescript
// agent/permissions.ts
const SENSITIVE_TOOLS = new Set(["delete_file", "execute_command", "send_email"]);

export async function checkToolPermission(toolName: string, args: any) {
  if (!isCapabilityEnabled(toolToCapability(toolName)))
    return { allow: false, reason: `能力 ${toolName} 未开启` };
  if (SENSITIVE_TOOLS.has(toolName)) {
    const confirmed = await requestUserConfirm(toolName, args);  // 经 win.bind 发 UI
    return confirmed ? { allow: true } : { allow: false, reason: "用户拒绝" };
  }
  return { allow: true };
}

export async function logToolCall(toolName: string, args: any, isError: boolean) {
  db.prepare("INSERT INTO tool_audit_log ...").run(...);
  win.bind("onAuditToolCall", { toolName, args, isError, at: Date.now() });
}
```

## 五、UI 与 in-process bindings（核心改动）

### 5.1 in-process bindings 模型（替代 Electron IPC）

deno desktop 的 `win.bind` 是**进程内通道**，非 socket IPC（spike 验证）：

```typescript
// Deno 侧: 注册函数供 webview 调用
win.bind("agentPrompt", async (text: string) => {
  await agent.prompt(text);
  return { ok: true };
});
win.bind("agentAbort", async () => agent.abort());
win.bind("readDoc", async (path: string) => await readDoc(path));

// webview 侧: 直接调用，返回 Promise（in-process，零跨进程往返）
const result = await bindings.agentPrompt("帮我做周报");
const doc = await bindings.readDoc("~/销售.xlsx");
```

**双向事件推送**（Deno → webview）：通过预先 bind 的回调注入：
```typescript
// Deno 侧注册一个"反向通道"函数，webview 端实现它
win.bind("onAgentEvent", null);  // 占位，webview 端覆盖
// 实际推送时：
agent.subscribe((event) => {
  // 经 in-process 通道把 event 传给 webview
  win.emit("agentEvent", event);  // deno desktop 的事件推送 API
});
```

> **对照 WorkBuddy（Electron）**：他们 `ipcMain.handle` + `webContents.send` 是跨进程序列化；我们 `win.bind` 是 in-process 通道，**无 socket 往返**。这是 deno desktop 的核心架构优势，spike 已验证 `win.bind("ping", handler)` + webview `bindings.ping()` 全通。

### 5.2 UI 加载模型

- `Deno.serve()` 提供 React 页面（Vite 构建的 SPA 或 SSR）。
- 首个 `new Deno.BrowserWindow()` 自动打开并导航到本地 serve 地址。
- webview 加载页面后，`bindings` 全局对象自动注入（deno desktop 提供）。

## 六、数据模型与存储（node:sqlite）

> **关键变更**：better-sqlite3 在 Deno 不兼容（N-API legacy，spike 实测失败），改用 **`node:sqlite`**（Deno 内置 Node 兼容模块，`DatabaseSync`，spike 验证建表/插入/查询全通）。

```typescript
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync(":memory:");  // 或文件路径
db.exec("CREATE TABLE ...");
db.prepare("INSERT ...").run(...);
```

schema SQL 与 better-sqlite3 基本兼容（标准 SQLite 语法）：

```sql
CREATE TABLE conversations ( id TEXT PRIMARY KEY, project_id TEXT, title TEXT, ... );
CREATE TABLE messages ( id TEXT PRIMARY KEY, conversation_id TEXT, parent_id TEXT, role TEXT, content TEXT, ... );
CREATE TABLE artifacts ( id TEXT PRIMARY KEY, conversation_id TEXT, kind TEXT, file_path TEXT, version INT, ... );
CREATE TABLE artifact_versions ( artifact_id TEXT, version INT, file_path TEXT, PRIMARY KEY(artifact_id, version) );
CREATE TABLE memories ( id TEXT PRIMARY KEY, scope TEXT, conversation_id TEXT, kind TEXT, content TEXT, ... );
CREATE TABLE skills ( id TEXT PRIMARY KEY, name TEXT, file_path TEXT, allowed_tools TEXT, enabled INT, source TEXT );
CREATE TABLE automations ( id TEXT PRIMARY KEY, trigger TEXT, action_skill_id TEXT, ... );  -- P1
CREATE TABLE providers ( id TEXT, kind TEXT, enabled INT );
CREATE TABLE usage ( id TEXT, provider TEXT, model TEXT, tokens_in INT, tokens_out INT, cost REAL, at INTEGER );

```

**文件布局**（`~/.workbuddy/`）：sessions/、memory/、skills/、artifacts/、cache/、logs/。

## 七、数据流：一次"生成周报 docx"的端到端路径

```
用户(webview) 输入"帮我把这周销售数据整理成周报"
   │  await bindings.agentPrompt(text)        ← in-process，零 IPC 往返
   ▼
[Deno runtime] win.bind("agentPrompt") handler → agent.prompt(msg) ── pi runAgentLoop
   │
   ├─► pi-ai streamSimple(deepseek, Deno 原生 fetch，无 CORS)
   │     └─► subscribe: message_update → win.emit("agentEvent", event) → webview Zustand
   │
   ├─► assistant toolCall: read_doc{path}
   │     ├─► beforeToolCall → checkToolPermission → 放行
   │     ├─► readDocTool.execute → exceljs 读 xlsx（同 runtime 直调）
   │     └─► afterToolCall → 审计 + win.emit 透明面板
   │
   ├─► toolCall: write_docx{sections} → docx 生成 → 写 artifacts/周报.docx
   ├─► assistant 无更多 toolCall → turn_end → agent_end
   └─► win.emit("agentEvent", agent_end) → webview 加载工件预览
```

**全链路在 Deno runtime 内**：无 CORS、无跨进程 IPC（in-process bindings）、无 sidecar（MVP 路径）。

> **对照 WorkBuddy（Electron）**：他们要 渲染→主进程→ACP/HTTP→cbc sidecar→反向委托→主进程执行→返 cbc→ACP/SSE→主进程→渲染，**多次跨进程往返**。我们：webview→(in-process)→Deno runtime(pi+能力)→webview。**in-process 通道，无 socket。**

## 八、安全模型（借鉴 WorkBuddy 三板斧，适配 deno desktop）

| 层 | WorkBuddy(Electron) | **我们(deno desktop)** |
|----|-----------|----------|
| UI 隔离 | contextIsolation + sandbox | **deno desktop 权限模型 + bindings 隔离**（webview 只能调 bind 的函数，无 Deno 直接访问） |
| 工具权限 | DeferExecuteTool + commandSafety | **beforeToolCall {block:true} + 敏感工具白名单 + 用户确认** |
| 命令安全 | execPolicy + 规则集 + 审计 | MVP 基础白名单；P1 commandSafety 规则集 |
| 文件保护 | Network Extension + 快照 | **P1：文件操作前快照 + 回滚** |
| 透明性 | 数据流面板 | **afterToolCall 推送工具调用时间线** |

权限三层：L2 能力开关（设置总控）/ L3 任务确认（beforeToolCall 拦截）/ 审计（afterToolCall）。

## 九、MVP / P1 / P2 演进路线

### MVP（deno desktop，零 sidecar）
- pi Agent 在 Deno runtime 直跑，钩子直调工具（spike 验证）
- in-process bindings 驱动 UI（spike 验证）
- JS 文档引擎（Layer1），零 sidecar
- 两层记忆 + 缓存
- 技能（SKILL.md）+ pi Session 树
- node:sqlite 存储（spike 验证）
- **无 MCP / 无 OS Computer Use / 无 Python sidecar / 无全局热键**

### P1（按需扩展，触发条件明确）
| 改动 | 触发条件 |
|------|----------|
| 拆 pi 到独立进程 | agent 稳定性成瓶颈；多账号并行 |
| 上 MCP | 用户需要生态扩展 |
| Python sidecar | docx 自由编辑 / pptx 编辑 |
| 文件快照 + 回滚 | OS 自动化上线 |
| **全局热键**（deno desktop 缺口） | 速唤浮窗需要 → `Deno.dlopen` FFI 或 native 插件 |
| OS Computer Use | 截图+鼠标键盘自动化 |
| 会话 load/resume 双语义 | 长会话恢复 |

### P2（远期）
- OS 级沙箱（对标 WorkBuddy Network Extension）
- Agent Teams 多 agent（pi `orchestrator` 包）
- **CloudProvider**（AgentProvider 云端实现，对标 WorkBuddy 双模式）
- 技能市场 + 身份系统（SOUL.md 人格化）

**平滑演进保证**：能力下沉 domain + AgentProvider 抽象 + pi 回调式 API（跨进程只改回调实现）+ domains/common+node 分层（cloud provider 复用 common）。
